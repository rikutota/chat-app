# チャットWebアプリ 開発実装計画書

## 1. 概要

本資料は、チャットWebアプリの開発・実装フェーズの全体計画をまとめたものである。

要件定義、技術選定、基本設計、DB設計、API設計、画面設計、詳細設計をもとに、実際の開発をどの順番で進めるかを定義する。

## 4. 開発方針

## 4.1 基本方針

- 小さく動く単位で実装する
- 認証、DB、API、画面を段階的に接続する
- 先に土台を作り、その後に機能を追加する
- 各機能は「DB → API → 画面 → 動作確認」の順に進める
- 実装しながらMarkdown資料も更新する
- MVP完成を最優先にする
- 本番公開向けの高度な機能は後回しにする

---

## 4.2 実装の基本単位

1つの機能は、以下の単位で完了とする。

```text
1. DBまたは設定を作る
2. APIまたはSupabase処理を作る
3. 画面を作る
4. バリデーションを入れる
5. エラー処理を入れる
6. ローカルで確認する
7. 必要なら資料を更新する
8. PRを作成する
9. レビュー後にマージする
```

## 7. 推奨Sprint構成

MVP完成までを6 Sprintに分ける。

| Sprint | 内容 | 目的 |
|---|---|---|
| Sprint 0 | プロジェクト準備・環境構築 | 開発開始できる状態を作る |
| Sprint 1 | 認証・ユーザー基盤 | ログインしてアプリユーザーを作る |
| Sprint 2 | チャットルーム機能 | ユーザーを選んで1対1ルームを作る |
| Sprint 3 | メッセージ送受信 | テキストメッセージを送れるようにする |
| Sprint 4 | Realtime・画像/ファイル送信 | チャット体験をMVP要件まで引き上げる |
| Sprint 5 | 仕上げ・テスト・デプロイ | MVPとして公開可能な状態にする |

## 8. MVP完了条件

MVPは、以下をすべて満たしたら完了とする。

## 8.1 認証

- Googleログインできる
- ログアウトできる
- 初回ログイン時に `users` レコードが作成される
- 未ログインで保護画面にアクセスするとログイン画面へ遷移する

## 8.2 ユーザー

- 自分以外のユーザー一覧を表示できる
- ユーザーを選んでチャットを開始できる

## 8.3 チャットルーム

- 1対1チャットルームを作成できる
- 同じ相手との既存ルームを再利用できる
- 自分のチャットルーム一覧を表示できる
- 自分が参加していないルームにはアクセスできない

## 8.4 メッセージ

- テキストメッセージを送信できる
- メッセージ一覧を表示できる
- 空文字は送信できない
- 2000文字超過は送信できない
- 相手画面にリアルタイムでメッセージが表示される

## 8.5 画像・ファイル

- 画像を送信できる
- 画像がチャット画面に表示される
- ファイルを送信できる
- ファイル名とサイズを表示できる
- 許可されていない形式は送信できない
- サイズ上限を超えるファイルは送信できない

## 8.6 デプロイ

- Vercelへデプロイできる
- 本番URLでログインできる
- 本番URLでチャットできる
- Supabase環境変数が正しく設定されている

## 10. 実装完了の定義

各タスクは以下を満たしたら完了とする。

```text
・仕様通りに動く
・最低限のエラー処理がある
・ローディングまたは送信中状態がある
・不要なconsole.logが残っていない
・型エラーがない
・Lintが通る
・ローカルで動作確認済み
・関連資料が必要に応じて更新済み
・PRがレビューされている
```

## 12. リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| Supabase Authで詰まる | OAuth設定やリダイレクトURLで詰まりやすい | 最初にログインだけ単独で動かす |
| RLSで詰まる | ポリシーが原因でDB操作できない可能性 | 初期はAPI側チェック優先、その後RLS導入 |
| Realtimeが動かない | 購読条件やテーブル設定で詰まる | まずmessages INSERTだけで検証する |
| Storage権限で詰まる | アップロード・取得ができない | 最初は簡単な設定で検証し、後で強化する |
| ルーム重複 | 同時作成で重複する可能性 | MVPでは許容、将来room_keyで改善 |
| ファイル送信の不整合 | Storage成功後DB失敗など | MVPでは手動補正、将来RPC化 |
| 資料が古くなる | 実装と設計がズレる | 変更時はchange-log.mdに記録する |
