# チャットWebアプリ 開発運用ルール

## 1. 概要

本資料は、チャットWebアプリの開発実装フェーズで利用する運用ルールをまとめたものである。

対象:

- Git運用
- ブランチルール
- コミットルール
- PRルール
- レビュー観点
- ドキュメント更新ルール
- タスク管理ルール

---

## 2. Git運用

## 2.1 ブランチ構成

```text
main
  本番リリース用

develop
  開発統合用

feature/*
  機能開発用

fix/*
  バグ修正用

docs/*
  ドキュメント更新用

chore/*
  設定変更・環境整備用
```

---

## 2.2 基本フロー

```text
1. developを最新化
2. featureブランチを作成
3. 実装
4. ローカル確認
5. コミット
6. develop向けにPR作成
7. レビュー
8. 修正
9. developへマージ
10. 動作確認
```

---

## 2.3 ブランチ名

| 種別 | 例 |
|---|---|
| 認証機能 | `feature/auth` |
| ユーザー一覧 | `feature/user-list` |
| チャットルーム | `feature/direct-chat-room` |
| メッセージ | `feature/message` |
| Realtime | `feature/realtime-message` |
| ファイル送信 | `feature/file-upload` |
| バグ修正 | `fix/message-duplicate` |
| ドキュメント | `docs/update-api-design` |
| 設定変更 | `chore/setup-eslint` |

---

## 3. コミットルール

## 3.1 形式

```text
type: message
```

例:

```text
feat: add google login
fix: prevent empty message submission
docs: update database design
chore: setup prettier
refactor: extract room member check
```

---

## 3.2 type一覧

| type | 用途 |
|---|---|
| feat | 機能追加 |
| fix | バグ修正 |
| docs | ドキュメント更新 |
| chore | 設定・環境整備 |
| refactor | 振る舞いを変えない改善 |
| test | テスト追加・修正 |
| style | 見た目・整形 |
| perf | パフォーマンス改善 |

---

## 3.3 コミット単位

1コミットは意味のある単位にする。

良い例:

```text
feat: add users table migration
feat: implement get current app user
feat: add login page
```

避ける例:

```text
fix
update
色々変更
作業中
```

## 4. PRルール

## 4.1 PRタイトル

```text
[feature] ログイン機能を実装
[fix] メッセージ二重表示を修正
[docs] API設計書を更新
```

---

## 4.2 PR本文テンプレート

```md
## 概要

## 対応内容

- 

## 確認方法

- 

## スクリーンショット

## 影響範囲

## 未対応・補足

## 関連資料

- 
```

---

## 4.3 PR作成前チェック

```text
・ローカルで起動できる
・対象機能を手動確認した
・型エラーがない
・Lintが通る
・不要なconsole.logがない
・環境変数をコミットしていない
・関連ドキュメントを更新した
・READMEに影響があれば更新した
```

---

## 5. レビュー観点

## 5.1 共通

| 観点 | 内容 |
|---|---|
| 仕様 | 設計書通りか |
| 可読性 | 読みやすいか |
| 型 | TypeScriptの型が適切か |
| エラー処理 | 失敗時を考慮しているか |
| セキュリティ | クライアント値を信用していないか |
| 影響範囲 | 他機能に悪影響がないか |
| UI | ローディング・エラー・空状態があるか |
| ドキュメント | 必要に応じて資料が更新されているか |

---

## 5.2 APIレビュー

確認すること:

```text
・未ログイン時に401になる
・権限なし時に403になる
・バリデーションエラーが適切
・レスポンス形式が統一されている
・senderIdなどをクライアントから信用していない
・DBエラー時に技術詳細をユーザーに返していない
```

---

## 5.3 DBレビュー

確認すること:

```text
・テーブル名、カラム名が設計通り
・外部キーが適切
・UNIQUE制約が必要な箇所にある
・インデックスが必要な箇所にある
・削除時の影響を理解している
・RLS導入予定と矛盾しない
```

---

## 5.4 フロントエンドレビュー

確認すること:

```text
・画面設計通りに表示される
・ローディング表示がある
・エラー表示がある
・空状態がある
・ボタン連打対策がある
・送信中にdisabledになる
・XSSにつながる描画をしていない
・ファイルサイズ・形式のチェックがある
```

## 7. タスク管理ルール

## 7.1 タスク粒度

1タスクは、1〜2日以内に完了できる粒度を目安にする。

大きすぎる例:

```text
チャット機能を作る
```

良い例:

```text
messagesテーブルを作成する
メッセージ一覧APIを実装する
MessageListコンポーネントを作成する
```

---

## 7.2 タスク完了条件

```text
・実装が完了している
・ローカル確認が完了している
・必要なエラー処理がある
・型エラーがない
・関連資料が更新されている
・PRがマージされている
```

---

## 7.3 優先度

| 優先度 | 内容 |
|---|---|
| High | MVPに必須 |
| Medium | MVP品質向上に必要 |
| Low | 後回し可能 |

## 8. 環境変数管理

## 8.1 `.env.local`

ローカル環境で利用する。

```text
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
```

必要に応じて追加する。

---

## 8.2 `.env.example`

リポジトリにコミットする。  
値は空にする。

```text
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
```

---

## 8.3 禁止事項

```text
・.env.local をGitにコミットしない
・Supabase service role keyをフロントに置かない
・秘密情報をREADMEやdocsに直接書かない
・スクリーンショットにシークレットを含めない
```

---

## 9. セキュリティ実装ルール

## 9.1 APIで必ず守ること

```text
・ログイン確認を行う
・アプリ内user_idをサーバー側で取得する
・sender_idをクライアントから受け取らない
・room参加者チェックを行う
・ファイルサイズをサーバー側でも確認する
・ファイル形式をサーバー側でも確認する
・エラー詳細をユーザーに返しすぎない
```

---

## 9.2 フロントで守ること

```text
・dangerouslySetInnerHTMLを使わない
・メッセージ本文は文字列として表示する
・送信中はボタンをdisabledにする
・ファイル選択時に簡易チェックする
・エラー時は分かりやすい文言を表示する
```

---

READMEには以下を記載する。

```text

・使用技術
・機能一覧
・セットアップ手順
・環境変数
・Supabase設定
・ローカル起動方法
・デプロイ方法
・開発資料一覧
```

---

## 11. リリース前チェック

Vercelデプロイ前に確認する。

```text
・main/developの状態が最新
・環境変数がVercelに設定されている
・Supabase Auth Redirect URLが設定されている
・Supabase Storageが設定されている
・DBテーブルが作成済み
・ローカルでMVP機能が動作する
・READMEが更新済み
・不要なconsole.logがない
・秘密情報がコミットされていない
```

---

## 12. 本番公開前に追加検討すること

MVPのVercel公開と、本格的な本番公開は分けて考える。

本格公開前に必要なこと:

```text
・RLS強化
・Storage非公開化
・署名付きURL
・レート制限
・Sentry導入
・利用規約
・プライバシーポリシー
・通報機能
・バックアップ方針
・ログ管理
・コスト監視
```
