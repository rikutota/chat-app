# チャットWebアプリ開発計画書

## 1. 目的

本プロジェクトでは、ユーザー同士がリアルタイムまたは準リアルタイムでメッセージを送受信できるチャットWebアプリを開発する。

開発は、要件定義からリリースまでの一般的なシステム開発プロセスに沿って進める。  
各工程の成果物は `.md` ファイルとして残し、後から設計内容・判断理由・実装方針を確認できる状態にする。

---

チャットWebアプリ

## 3. 開発方針

### 基本方針

- 最初に全体計画を立てる
- 要件定義で作る範囲を明確にする
- 技術選定は要件定義の後半から基本設計前半で行う
- 設計資料は `.md` で管理する
- 開発は機能単位で小さく進める
- まずMVPを完成させ、その後に機能追加する
- Gitで履歴管理する
- 実装と並行してテスト観点を整理する
- リリース前に手順書と切り戻し方針を作成する

### 開発スタイル

小規模開発を想定し、以下のような進め方にする。

- 要件定義、設計は最初に大枠を固める
- 実装は機能単位で進める
- 不明点は都度 `docs/issues.md` に記録する
- 仕様変更は `docs/change-log.md` に記録する
- 完璧な設計を待たず、MVPを優先する

## 13. リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| 要件が広がる | チャット機能は追加要望が増えやすい | MVP範囲を明確にする |
| リアルタイム通信が難しい | WebSocket周りで詰まる可能性 | 最初は通常のAPIで作り、後からリアルタイム化する |
| 認証・権限が複雑になる | 不正アクセスの原因になる | 最初に認証方針を決める |
| DB設計の手戻り | メッセージ・既読・ルーム管理は設計が重要 | MVP範囲で最小テーブルから始める |
| デプロイで詰まる | 環境変数やDB接続で問題が出やすい | 早めにステージング環境を作る |
| 資料が更新されない | 実装と資料がズレる | 仕様変更はchange-logに残す |

## 16. メモ

チャットアプリは一見シンプルに見えるが、実際には以下のような論点がある。

- 認証
- 権限
- メッセージ保存
- リアルタイム通信
- 通知
- 既読管理
- 不正利用対策
- レート制限
- ログ管理
- 本番運用

そのため、最初から全部作るのではなく、まずは「ログインして、ルームを作って、メッセージを送れる」状態を目指す。
