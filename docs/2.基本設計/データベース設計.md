# チャットWebアプリ DB設計書

## 1. 概要

本資料は、チャットWebアプリのDB設計をまとめたものである。

本アプリでは、Supabase PostgreSQLを利用する。  
認証はSupabase Authを利用し、アプリ固有のユーザー情報は `users` テーブルで管理する。

MVPでは以下を扱う。

- 外部認証ユーザーとアプリ内ユーザーの紐づけ
- 1対1チャットルーム
- チャットルーム参加者
- テキストメッセージ
- 画像メッセージ
- ファイルメッセージ
- 添付ファイル情報
- チャットルーム参加者チェック
- Supabase Realtimeによるメッセージ更新

---

## 2. DB設計方針

### 2.1 基本方針

- DBはSupabase PostgreSQLを使う
- 認証情報そのものはSupabase Authに任せる
- アプリ内で使うプロフィール情報は `users` テーブルで管理する
- 1対1チャット専用のルームテーブルを作る
- メッセージ本文と添付ファイル情報は分ける
- ファイル本体はDBに保存しない
- ファイル本体はSupabase Storageに保存する
- DBにはStorage上のパスやメタ情報を保存する
- アクセス制御はアプリ側チェックとRLSの両方を検討する

---

### 2.2 命名方針

| 種別 | 方針 |
|---|---|
| テーブル名 | 複数形、snake_case |
| カラム名 | snake_case |
| 主キー | `id` |
| 外部キー | `{参照先単数形}_id` |
| 作成日時 | `created_at` |
| 更新日時 | `updated_at` |
| 削除日時 | 必要になったら `deleted_at` を追加 |

---

### 2.3 ID方針

主キーはUUIDを利用する。

理由:

- Supabase / PostgreSQLと相性が良い
- 推測されにくい
- フロントエンド側で扱いやすい
- 将来的な分散構成にも寄せやすい

---

## 3. テーブル一覧

| テーブル名 | 内容 |
|---|---|
| users | アプリ内ユーザー |
| direct_chat_rooms | 1対1チャットルーム |
| direct_chat_room_members | 1対1チャットルーム参加者 |
| messages | メッセージ |
| message_attachments | メッセージ添付ファイル |

---

## 4. ER図イメージ

```text
auth.users
   │
   │ 1:1
   ↓
users
   │
   │ 1:N
   ↓
direct_chat_room_members
   ↑
   │ N:1
direct_chat_rooms
   │
   │ 1:N
   ↓
messages
   │
   │ 1:0..1
   ↓
message_attachments
```

補足:

- `auth.users` はSupabase Authが管理するテーブル
- `users.auth_user_id` が `auth.users.id` に対応する
- 1つの1対1チャットルームには、必ず2人のmemberが存在する想定
- 1つのメッセージは、添付ファイルなし、または1つの添付ファイルを持つ
- 複数ファイル同時送信はMVPでは対象外

## 5. テーブル定義

## 5.1 users

## 概要

アプリ内で利用するユーザー情報を管理する。

Supabase AuthのユーザーIDを `auth_user_id` として保持し、アプリ側のプロフィール表示やチャット相手一覧で利用する。

## カラム定義

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---:|---|---|
| id | uuid | NO | PK | アプリ内ユーザーID |
| auth_user_id | uuid | NO | UNIQUE | Supabase AuthのユーザーID |
| display_name | text | NO |  | 表示名 |
| avatar_url | text | YES |  | アイコンURL |
| email | text | YES |  | メールアドレス |
| created_at | timestamptz | NO | default now() | 作成日時 |
| updated_at | timestamptz | NO | default now() | 更新日時 |

## 制約

| 制約 | 内容 |
|---|---|
| PK | `id` |
| UNIQUE | `auth_user_id` |
| NOT NULL | `auth_user_id`, `display_name`, `created_at`, `updated_at` |

## インデックス

| インデックス | 対象 | 目的 |
|---|---|---|
| users_auth_user_id_idx | `auth_user_id` | 認証ユーザーからアプリユーザーを取得 |
| users_display_name_idx | `display_name` | ユーザー検索の将来対応 |

## 備考

- 初回ログイン時に `users` レコードを作成する
- `display_name` は外部認証サービスのユーザー名を初期値にしてよい
- `email` は表示・検索には使わず、必要最小限に留める
- 本番公開時は個人情報の扱いに注意する

---

## 5.2 direct_chat_rooms

## 概要

1対1チャットルームを管理する。

ルームそのものには相手情報を直接持たせず、参加者は `direct_chat_room_members` で管理する。

## カラム定義

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---:|---|---|
| id | uuid | NO | PK | チャットルームID |
| created_at | timestamptz | NO | default now() | 作成日時 |
| updated_at | timestamptz | NO | default now() | 更新日時 |

## 制約

| 制約 | 内容 |
|---|---|
| PK | `id` |
| NOT NULL | `created_at`, `updated_at` |

## インデックス

| インデックス | 対象 | 目的 |
|---|---|---|
| direct_chat_rooms_created_at_idx | `created_at` | 新しいルーム順の取得 |

## 備考

1対1チャットでは、同じ2人の組み合わせで複数ルームができないようにする必要がある。

ただし、単純な `direct_chat_rooms` だけでは2人の組み合わせユニーク制約を付けにくい。  
MVPではアプリ側で既存ルーム確認を行う。

将来的には以下のいずれかを検討する。

- `room_key` カラムを追加する
- 2人のuser_idをソートして `user_a_id`, `user_b_id` として持つ
- PostgreSQL関数や制約で組み合わせ重複を防ぐ

MVPでは分かりやすさを優先し、参加者テーブル方式を採用する。

---

## 5.3 direct_chat_room_members

## 概要

1対1チャットルームに参加しているユーザーを管理する。

1つのルームには2人のユーザーが紐づく。

## カラム定義

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---:|---|---|
| id | uuid | NO | PK | 参加者ID |
| room_id | uuid | NO | FK | チャットルームID |
| user_id | uuid | NO | FK | ユーザーID |
| created_at | timestamptz | NO | default now() | 作成日時 |

## 制約

| 制約 | 内容 |
|---|---|
| PK | `id` |
| FK | `room_id` references `direct_chat_rooms(id)` |
| FK | `user_id` references `users(id)` |
| UNIQUE | `(room_id, user_id)` |
| NOT NULL | `room_id`, `user_id`, `created_at` |

## インデックス

| インデックス | 対象 | 目的 |
|---|---|---|
| direct_chat_room_members_room_id_idx | `room_id` | ルーム参加者取得 |
| direct_chat_room_members_user_id_idx | `user_id` | 自分のルーム一覧取得 |
| direct_chat_room_members_room_user_idx | `(room_id, user_id)` | 参加者チェック |

## 備考

チャットルームアクセス時は、このテーブルを使って参加者チェックを行う。

```text
room_id = 対象ルームID
user_id = ログイン中ユーザーID
```

のレコードが存在すればアクセス許可。

## 5.4 messages

## 概要

チャットルーム内のメッセージを管理する。

テキスト、画像、ファイルのメッセージを同じテーブルで扱う。  
画像やファイルの詳細情報は `message_attachments` に分ける。

## カラム定義

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---:|---|---|
| id | uuid | NO | PK | メッセージID |
| room_id | uuid | NO | FK | チャットルームID |
| sender_id | uuid | NO | FK | 送信者ユーザーID |
| message_type | text | NO | check | `text`, `image`, `file` |
| body | text | YES |  | テキスト本文 |
| created_at | timestamptz | NO | default now() | 作成日時 |
| updated_at | timestamptz | NO | default now() | 更新日時 |

## 制約

| 制約 | 内容 |
|---|---|
| PK | `id` |
| FK | `room_id` references `direct_chat_rooms(id)` |
| FK | `sender_id` references `users(id)` |
| CHECK | `message_type in ('text', 'image', 'file')` |
| NOT NULL | `room_id`, `sender_id`, `message_type`, `created_at`, `updated_at` |

## インデックス

| インデックス | 対象 | 目的 |
|---|---|---|
| messages_room_id_created_at_idx | `(room_id, created_at)` | ルーム内メッセージを時系列で取得 |
| messages_sender_id_idx | `sender_id` | 送信者別の取得・調査 |
| messages_created_at_idx | `created_at` | 新着メッセージ取得 |

## バリデーション方針

### text

- `message_type = 'text'`
- `body` は必須
- 空文字は不可
- 最大文字数はAPI設計で決定

### image

- `message_type = 'image'`
- 添付ファイル情報が必要
- `body` は任意

### file

- `message_type = 'file'`
- 添付ファイル情報が必要
- `body` は任意

## 備考

メッセージ削除・編集はMVPでは対象外。  
将来的に対応する場合は以下を追加検討する。

- `deleted_at`
- `edited_at`
- `is_deleted`
- `deleted_by`

---

## 5.5 message_attachments

## 概要

メッセージに紐づく画像・ファイル情報を管理する。

ファイル本体はSupabase Storageに保存し、このテーブルにはファイル名、保存パス、MIMEタイプ、サイズなどを保存する。

## カラム定義

| カラム名 | 型 | NULL | 制約 | 説明 |
|---|---|---:|---|---|
| id | uuid | NO | PK | 添付ファイルID |
| message_id | uuid | NO | FK, UNIQUE | メッセージID |
| file_name | text | NO |  | 表示用ファイル名 |
| file_path | text | NO |  | Storage上の保存パス |
| mime_type | text | NO |  | MIMEタイプ |
| file_size | integer | NO |  | ファイルサイズ byte |
| created_at | timestamptz | NO | default now() | 作成日時 |

## 制約

| 制約 | 内容 |
|---|---|
| PK | `id` |
| FK | `message_id` references `messages(id)` |
| UNIQUE | `message_id` |
| NOT NULL | `message_id`, `file_name`, `file_path`, `mime_type`, `file_size`, `created_at` |
| CHECK | `file_size > 0` |

## インデックス

| インデックス | 対象 | 目的 |
|---|---|---|
| message_attachments_message_id_idx | `message_id` | メッセージから添付情報取得 |
| message_attachments_file_path_idx | `file_path` | Storageファイル特定 |

## 備考

MVPでは1メッセージにつき添付ファイルは1つまでとする。  
そのため `message_id` にUNIQUE制約を付ける。

将来的に複数ファイルを1メッセージに添付する場合は、`message_id` のUNIQUE制約を外す。

## 6. 1対1チャットルーム重複防止

### 6.1 課題

1対1チャットでは、同じ2人のユーザー間で複数のルームが作られないようにする必要がある。

例:

```text
User A + User B のルームが既に存在する
  ↓
再度User AがUser Bへチャット開始
  ↓
既存ルームを再利用する
```

---

### 6.2 MVPでの対応

MVPではアプリ側で既存ルームを確認する。

処理イメージ:

```text
1. 自分のuser_idを取得
2. 相手のuser_idを取得
3. 自分が参加しているroom_id一覧を取得
4. その中から相手も参加しているroom_idを探す
5. 見つかれば既存ルームを返す
6. なければ新規ルームを作成する
7. 自分と相手をmembersに登録する
```

---

### 6.3 将来的な改善案

将来的には `direct_chat_rooms` に `room_key` を追加する。

```text
room_key = 小さいuser_id + ':' + 大きいuser_id
```

例:

```text
userA = 111
userB = 999
room_key = 111:999
```

この `room_key` にUNIQUE制約を付けることで、DBレベルで重複作成を防げる。

MVPでは実装理解を優先し、まずは参加者テーブル方式で進める。

---

## 7. Supabase Authとの連携

### 7.1 認証ユーザーとアプリユーザー

Supabase Authでログインしたユーザーは `auth.users` に作成される。  
アプリ側では、初回ログイン時に `users` テーブルにもレコードを作成する。

```text
auth.users.id
  ↓
users.auth_user_id
```

---

### 7.2 初回ログイン時の処理

```text
1. Supabase Authでログイン
2. auth_user_idを取得
3. usersテーブルに同じauth_user_idが存在するか確認
4. 存在すればそのユーザー情報を利用
5. 存在しなければusersレコードを作成
6. チャット画面へ進む
```

---

## 8. Supabase Storageとの連携

### 8.1 保存方針

ファイル本体はSupabase Storageに保存する。  
DBにはファイルのメタ情報のみ保存する。

---

### 8.2 バケット案

| バケット名 | 用途 |
|---|---|
| chat-attachments | チャット画像・ファイル保存 |

---

### 8.3 ファイルパス案

```text
chat-attachments/
  rooms/
    {room_id}/
      {message_id}/
        {file_name}
```

例:

```text
rooms/room-uuid/message-uuid/image.png
```

---

### 8.4 保存時の流れ

```text
1. ユーザーがファイルを選択
2. フロント側でサイズ・形式をチェック
3. Supabase Storageへアップロード
4. messagesにメッセージを作成
5. message_attachmentsにファイル情報を保存
6. Realtimeにより相手画面に反映
```

---

### 8.5 注意点

理想的には、メッセージIDを先に作成してから、そのIDを使ってStorageパスを決める。  
ただし、アップロード失敗時やDB保存失敗時の整合性に注意する必要がある。

MVPでは以下のどちらかで実装する。

#### 案A: ファイルアップロード後にメッセージ作成

```text
1. ファイルをStorageへアップロード
2. messagesを作成
3. message_attachmentsを作成
```

メリット:

- 実装が分かりやすい

デメリット:

- DB保存に失敗した場合、Storageに孤立ファイルが残る可能性がある

#### 案B: メッセージ作成後にファイルアップロード

```text
1. messagesを仮作成
2. message_idを使ってStorageへアップロード
3. message_attachmentsを作成
4. メッセージを有効化
```

メリット:

- Storageパスを整理しやすい

デメリット:

- 実装が少し複雑

MVPでは案Aを採用し、孤立ファイルは後から手動削除または改善対象とする。

## 9. RLS方針

SupabaseではRow Level Securityを使って、DBレベルでアクセス制御を行える。

MVPでもRLSの基本方針は定義する。  
実装時には、まずアプリ側のチェックを作り、その後RLSを有効化して安全性を高める。

---

## 9.1 users

### select

ログイン済みユーザーはユーザー一覧を取得できる。

```text
authenticated user can select users
```

### insert

自分の `auth.uid()` に対応する `auth_user_id` のレコードのみ作成できる。

### update

MVPではプロフィール編集を実装しないため、原則更新なし。  
将来的には自分のユーザー情報のみ更新可能にする。

---

## 9.2 direct_chat_rooms

### select

自分が参加しているルームのみ取得できる。

条件イメージ:

```text
exists direct_chat_room_members
where room_id = direct_chat_rooms.id
and user_id = current_app_user_id
```

### insert

ログイン済みユーザーのみ作成可能。  
ただし、ルーム作成とメンバー登録は整合性が必要なため、実装時にRPC関数化を検討する。

---

## 9.3 direct_chat_room_members

### select

自分が参加しているルームのメンバー情報のみ取得できる。

### insert

MVPではアプリ側処理でルーム作成時に登録する。  
RLSで厳密にやる場合はRPC関数を使う方が安全。

---

## 9.4 messages

### select

自分が参加しているルームのメッセージのみ取得できる。

### insert

自分が参加しているルームに、自分自身を `sender_id` とするメッセージのみ作成できる。

### update / delete

MVPでは禁止。

---

## 9.5 message_attachments

### select

自分が参加しているルームのメッセージに紐づく添付ファイルのみ取得できる。

### insert

自分が送信したメッセージに紐づく添付情報のみ作成できる。

### update / delete

MVPでは禁止。

---

## 10. SQL定義案

以下は初期実装用のSQL案である。  
実際の実装ではSupabase SQL Editorまたはマイグレーションで管理する。

```sql
create extension if not exists "pgcrypto";

create table public.users (
  id uuid primary key default gen_random_uuid(),
  auth_user_id uuid not null unique,
  display_name text not null,
  avatar_url text,
  email text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index users_auth_user_id_idx
  on public.users (auth_user_id);

create index users_display_name_idx
  on public.users (display_name);

create table public.direct_chat_rooms (
  id uuid primary key default gen_random_uuid(),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index direct_chat_rooms_created_at_idx
  on public.direct_chat_rooms (created_at);

create table public.direct_chat_room_members (
  id uuid primary key default gen_random_uuid(),
  room_id uuid not null references public.direct_chat_rooms(id) on delete cascade,
  user_id uuid not null references public.users(id) on delete cascade,
  created_at timestamptz not null default now(),
  unique (room_id, user_id)
);

create index direct_chat_room_members_room_id_idx
  on public.direct_chat_room_members (room_id);

create index direct_chat_room_members_user_id_idx
  on public.direct_chat_room_members (user_id);

create index direct_chat_room_members_room_user_idx
  on public.direct_chat_room_members (room_id, user_id);

create table public.messages (
  id uuid primary key default gen_random_uuid(),
  room_id uuid not null references public.direct_chat_rooms(id) on delete cascade,
  sender_id uuid not null references public.users(id) on delete cascade,
  message_type text not null check (message_type in ('text', 'image', 'file')),
  body text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index messages_room_id_created_at_idx
  on public.messages (room_id, created_at);

create index messages_sender_id_idx
  on public.messages (sender_id);

create index messages_created_at_idx
  on public.messages (created_at);

create table public.message_attachments (
  id uuid primary key default gen_random_uuid(),
  message_id uuid not null unique references public.messages(id) on delete cascade,
  file_name text not null,
  file_path text not null,
  mime_type text not null,
  file_size integer not null check (file_size > 0),
  created_at timestamptz not null default now()
);

create index message_attachments_message_id_idx
  on public.message_attachments (message_id);

create index message_attachments_file_path_idx
  on public.message_attachments (file_path);
```

## 11. updated_at更新方針

`updated_at` はレコード更新時に自動更新する。

関数案:

```sql
create or replace function public.update_updated_at_column()
returns trigger as $$
begin
  new.updated_at = now();
  return new;
end;
$$ language plpgsql;
```

トリガー案:

```sql
create trigger update_users_updated_at
before update on public.users
for each row
execute function public.update_updated_at_column();

create trigger update_direct_chat_rooms_updated_at
before update on public.direct_chat_rooms
for each row
execute function public.update_updated_at_column();

create trigger update_messages_updated_at
before update on public.messages
for each row
execute function public.update_updated_at_column();
```

## 12. Realtime対象テーブル

Supabase Realtimeでは、主に `messages` テーブルのINSERTを購読する。

対象:

| テーブル | イベント | 用途 |
|---|---|---|
| messages | INSERT | 新着メッセージ表示 |
| message_attachments | INSERT | 添付情報の取得 |

基本は `messages` のINSERTを購読し、添付が必要な場合は関連情報を取得する。

## 13.4 チャットルーム参加者チェック

```text
direct_chat_room_members
where room_id = target_room_id
and user_id = current_user.id
```

存在すればアクセス可能。

## 13.5 メッセージ一覧取得

```text
messages
where room_id = target_room_id
order by created_at asc
```

事前に参加者チェックを行う。

## 15. 削除方針

MVPではメッセージ削除、チャットルーム削除、ユーザー削除は実装しない。

DB制約上は、親データ削除時に関連データも削除されるように `on delete cascade` を設定している。

本番公開時は物理削除ではなく、以下を検討する。

- 論理削除
- 削除済みメッセージ表示
- 監査ログ
- 保存期間ポリシー
