# チャットWebアプリ 技術選定書

## 1. 前提

本資料は、チャットWebアプリの技術選定をまとめたものである。

本プロジェクトは、以下の方針で進める。

- 学習用として開発する
- 将来的に本番公開できる構成にする
- 1対1チャットを作る
- 外部認証を使う
- リアルタイム更新を含める
- 画像・ファイル送信を含める
- 管理者機能は初期開発に含めない
- スマホ対応は後回し
- 成果物はMarkdownで残す

---

## 2. 技術選定の結論

### 採用候補

| 分類 | 採用技術 |
|---|---|
| フロントエンド | Next.js |
| 言語 | TypeScript |
| UI | Tailwind CSS |
| 認証 | Supabase Auth |
| DB | Supabase PostgreSQL |
| リアルタイム通信 | Supabase Realtime |
| 画像・ファイル保存 | Supabase Storage |
| ホスティング | Vercel |
| バージョン管理 | Git / GitHub |
| テスト | Vitest / React Testing Library / Playwright |
| Lint / Formatter | ESLint / Prettier |
| ドキュメント | Markdown |

---

## 3. 採用構成の全体像

```text
Browser
  ↓
Next.js
  ↓
Supabase Auth
  ↓
Supabase PostgreSQL
  ↓
Supabase Realtime
  ↓
Supabase Storage
```

デプロイは以下の構成を想定する。

```text
GitHub
  ↓
Vercel
  ↓
Next.js App
  ↓
Supabase
    ├─ Auth
    ├─ PostgreSQL
    ├─ Realtime
    └─ Storage
```

---

## 4. なぜこの構成にするか

### 理由

今回のMVPでは、以下の要件がある。

- 外部認証
- 1対1チャット
- リアルタイム更新
- 画像・ファイル送信
- 学習用
- 将来的な本番公開

この条件では、認証、DB、リアルタイム通信、ファイルストレージを別々に構築すると、学習コストと実装量が大きくなる。

Supabaseを使うと、以下を1つのサービスでまとめて扱える。

- 認証
- PostgreSQL
- リアルタイム更新
- ファイルストレージ
- Row Level Security
- API利用

そのため、今回のMVPでは Supabase を中心にした構成が適している。

## 5. フロントエンド選定

## 5.1 候補

| 候補 | 概要 |
|---|---|
| React | UI構築ライブラリ |
| Next.js | Reactベースのフルスタックフレームワーク |
| Vue | 学習しやすいフロントエンドフレームワーク |
| Nuxt | Vueベースのフルスタックフレームワーク |
| SvelteKit | 軽量で高性能なフルスタックフレームワーク |

---

## 5.2 React

### メリット

- 利用者が多い
- 情報量が多い
- コンポーネント指向を学べる
- Next.jsへ移行しやすい
- 求人や実務でも使われやすい

### デメリット

- React単体ではルーティングやSSRなどを別途考える必要がある
- 構成を自分で決める部分が多い
- デプロイやAPI連携は別途設計が必要

### 評価

学習には良いが、今回のように認証・チャット・ファイル送信まで含むWebアプリでは、Next.jsの方が構成を作りやすい。

---

## 5.3 Next.js

### メリット

- Reactベースで学習価値が高い
- ルーティングが標準で用意されている
- API連携しやすい
- Vercelとの相性が良い
- 本番公開しやすい
- フロントエンドとサーバー側処理を同じプロジェクトで扱える
- 将来的に認証ガードやメタデータ管理なども整理しやすい

### デメリット

- React単体より覚えることが多い
- App Router、Server Componentsなど概念がやや多い
- リアルタイム通信や外部サービス連携の理解は必要

### 評価

今回の採用候補として最も適している。  
学習用としても、本番公開を見据えた構成としてもバランスが良い。

### 採用判断

採用する。

---

## 5.4 Vue / Nuxt

### メリット

- Vueは書き方が分かりやすい
- Nuxtを使えばNext.jsのようなフルスタック構成も可能
- 学習コストが比較的低い

### デメリット

- React / Next.jsに比べると、今回の想定構成では情報収集の面で少し不利
- Supabaseとの組み合わせ情報はあるが、Next.jsほど事例が多くない可能性がある

### 評価

選択肢としては十分あり。  
ただし、今回の目的ではNext.jsを優先する。

---

## 5.5 SvelteKit

### メリット

- 軽量
- 書きやすい
- パフォーマンスが良い
- 少ないコードで実装しやすい

### デメリット

- React / Next.jsより実務利用や情報量が少ない
- チーム開発や学習資料の面ではやや不利

### 評価

個人開発には魅力的だが、今回の学習・将来公開・情報量を考えると優先度は下げる。

---

## 5.6 フロントエンド結論

Next.jsを採用する。

理由:

- Reactを学べる
- Webアプリとして本番公開しやすい
- Vercelとの相性が良い
- Supabase連携の情報が多い
- 学習用と将来公開のバランスが良い

---

## 6. 言語選定

## 6.1 候補

| 候補 | 概要 |
|---|---|
| JavaScript | Web標準のスクリプト言語 |
| TypeScript | JavaScriptに型を追加した言語 |

---

## 6.2 JavaScript

### メリット

- 書き始めやすい
- 学習コストが低い
- 環境構築が簡単

### デメリット

- 型がないため、実装規模が大きくなるとミスが増えやすい
- APIレスポンスやDB型の扱いで不具合に気づきにくい
- 将来的な保守性が落ちやすい

---

## 6.3 TypeScript

### メリット

- 型によりバグを減らしやすい
- APIレスポンスやDBデータの形を管理しやすい
- エディタ補完が効く
- 実務で使われやすい
- 将来的な保守性が高い

### デメリット

- JavaScriptより学習コストがある
- 型定義に時間がかかる場合がある
- 最初はエラーが多く感じることがある

---

## 6.4 言語結論

TypeScriptを採用する。

理由:

- チャットアプリはユーザー、メッセージ、添付ファイルなどデータ構造が多い
- 型がある方がバグを防ぎやすい
- 将来的な本番公開を考えると保守性が重要
- Next.jsとの相性が良い

---

## 7. 認証選定

## 7.1 候補

| 候補 | 概要 |
|---|---|
| Supabase Auth | Supabaseの認証機能 |
| Firebase Authentication | Google Firebaseの認証機能 |
| Clerk | 認証・ユーザー管理特化サービス |
| Auth0 | エンタープライズ寄りの認証サービス |
| 自前実装 | メール・パスワード認証を自分で作る |

---

## 7.2 Supabase Auth

### メリット

- Supabase DBと連携しやすい
- PostgreSQLのRow Level Securityと相性が良い
- OAuthログインに対応できる
- 認証、DB、Storage、Realtimeをまとめて扱える
- 学習用として理解しやすい
- 将来的な本番公開にも寄せやすい

### デメリット

- 認証だけを見るとClerkやAuth0ほど専業ではない
- 複雑なユーザー管理や組織管理が必要になると追加設計が必要
- Supabaseへの依存が強くなる

### 評価

今回の構成では最も相性が良い。

---

## 7.3 Firebase Authentication

### メリット

- 実績が多い
- Googleログインなど外部認証が使いやすい
- Firebase StorageやFirestoreと連携しやすい
- ドキュメントが多い

### デメリット

- DBをFirestoreにするとNoSQL設計になる
- PostgreSQLで設計したい場合は構成が分かれる
- チャットルームやメッセージのリレーションをRDBとして学びたい場合は不向きな面がある

### 評価

リアルタイムアプリには強い。  
ただし、今回の学習目的ではPostgreSQLも学びたいのでSupabaseを優先する。

---

## 7.4 Clerk

### メリット

- 認証UIやユーザー管理が強い
- Next.jsとの相性が良い
- 開発体験が良い
- 本番向けの認証機能を作りやすい

### デメリット

- DB、Realtime、Storageは別に用意する必要がある
- 今回のようなMVPでは構成要素が増える
- 認証以外の学習対象が分散する

### 評価

認証だけなら非常に強い。  
ただし、今回のMVPではSupabaseにまとめた方が実装しやすい。

---

## 7.5 Auth0

### メリット

- 認証機能が非常に豊富
- エンタープライズ用途に強い
- セキュリティ要件が高いシステムに向く

### デメリット

- 小規模MVPにはやや重い
- 設定項目が多い
- 学習用としては過剰になりやすい

### 評価

本格的な商用サービスや企業向けなら候補。  
今回のMVPでは採用しない。

---

## 7.6 自前実装

### メリット

- 認証の仕組みを深く学べる
- 自由度が高い

### デメリット

- セキュリティリスクが高い
- パスワード管理、リセット、メール認証などが大変
- 本番公開を考えると避けたい
- 今回の「外部認証を使う」という要件に合わない

### 評価

採用しない。

---

## 7.7 認証結論

Supabase Authを採用する。

理由:

- DB、Realtime、Storageと統合しやすい
- 外部認証要件を満たせる
- 学習用として全体像を理解しやすい
- 将来的な本番公開にも対応しやすい

---

## 8. DB選定

## 8.1 候補

| 候補 | 概要 |
|---|---|
| PostgreSQL | RDB |
| MySQL | RDB |
| Firestore | NoSQL |
| MongoDB | NoSQL |
| SQLite | 軽量DB |

---

## 8.2 PostgreSQL

### メリット

- RDBとして実績がある
- リレーション設計を学べる
- 1対1チャット、参加者、メッセージ、添付ファイルの関係を表現しやすい
- Supabaseで簡単に使える
- 将来的な本番利用にも向く
- SQLを学べる

### デメリット

- NoSQLより設計を考える必要がある
- リアルタイム更新はDBだけでは完結しない
- マイグレーション管理が必要

### 評価

今回のチャットアプリに最も適している。

---

## 8.3 MySQL

### メリット

- 実績が多い
- 情報量が多い
- RDB設計を学べる

### デメリット

- Supabaseとの統合はできない
- RealtimeやStorageを別途用意する必要がある
- 今回の構成ではPostgreSQLの方が自然

### 評価

RDBとしては良いが、Supabase採用前提ならPostgreSQLを選ぶ。

---

## 8.4 Firestore

### メリット

- リアルタイム更新に強い
- Firebase AuthenticationやStorageと相性が良い
- サーバーレスで始めやすい

### デメリット

- NoSQLなのでリレーション設計の学習には向かない
- 1対1チャットの取得パターンや権限設計に慣れが必要
- SQLを学べない
- 複雑な検索や集計ではRDBより考慮が必要

### 評価

チャットアプリには向いている。  
ただし、今回はRDB設計も学びたいので採用しない。

---

## 8.5 MongoDB

### メリット

- JSONに近い形でデータを扱える
- 柔軟なスキーマ
- Node.jsとの相性が良い

### デメリット

- リレーション管理はRDBより工夫が必要
- 今回の1対1チャットではPostgreSQLの方が分かりやすい
- Supabaseとの統合はできない

### 評価

柔軟性はあるが、今回の要件では優先度を下げる。

---

## 8.6 SQLite

### メリット

- 軽量
- ローカル開発が簡単
- 学習用には使いやすい

### デメリット

- 本番公開やリアルタイム用途には不向き
- 複数ユーザー・ファイル・リアルタイムチャットには弱い
- Supabase構成とは合わない

### 評価

今回のMVPでは採用しない。

---

## 8.7 DB結論

Supabase PostgreSQLを採用する。

理由:

- チャットルーム、参加者、メッセージ、添付ファイルの関係を表現しやすい
- RDB設計とSQLを学べる
- Supabase Auth / Realtime / Storageと統合できる
- 将来的な本番公開にも対応しやすい

## 9. リアルタイム通信選定

## 9.1 候補

| 候補 | 概要 |
|---|---|
| Supabase Realtime | Supabaseのリアルタイム機能 |
| Firebase Firestore Realtime | Firestoreのリアルタイム購読 |
| Socket.IO | WebSocketベースのリアルタイム通信ライブラリ |
| Server-Sent Events | サーバーからクライアントへの一方向通信 |
| ポーリング | 一定間隔でAPIを叩く方式 |

---

## 9.2 Supabase Realtime

### メリット

- Supabase DBと統合しやすい
- メッセージテーブルの変更をリアルタイムに反映しやすい
- WebSocketサーバーを自前で運用しなくてよい
- 学習用として実装量を抑えられる
- 今回の1対1チャットMVPに合っている

### デメリット

- Socket.IOほど自由なイベント設計はしにくい
- 複雑なオンライン状態管理やタイピング表示には追加設計が必要
- Supabase依存が強くなる

### 評価

今回のMVPでは最もバランスが良い。

---

## 9.3 Firebase Firestore Realtime

### メリット

- リアルタイム同期が強い
- Firebase AuthenticationとStorageとの相性が良い
- チャットアプリの事例が多い

### デメリット

- Firestore前提になりやすい
- RDB設計を学びにくい
- Supabase構成とは別路線になる

### 評価

Firebase中心で作るなら強い。  
今回はSupabase中心のため採用しない。

---

## 9.4 Socket.IO

### メリット

- 低遅延の双方向通信に向いている
- イベント設計の自由度が高い
- タイピング中、オンライン状態、既読通知などを実装しやすい
- WebSocketの実務的な仕組みを学べる

### デメリット

- WebSocketサーバーを自分で用意する必要がある
- デプロイやスケーリングが難しくなる
- Vercelのようなサーバーレス環境とは相性に注意が必要
- MVPとしては構成が重くなる

### 評価

本格的なリアルタイム機能には良い。  
ただし、今回のMVPではSupabase Realtimeの方が簡単。

### 将来的な扱い

将来的に以下を追加するなら検討する。

- タイピング中表示
- オンライン状態
- 既読イベント
- 独自イベント
- 大量接続への細かい制御

---

## 9.5 Server-Sent Events

### メリット

- サーバーからクライアントへの通知がシンプル
- WebSocketより実装が軽い場合がある

### デメリット

- 基本的に一方向通信
- チャットの双方向通信にはWebSocket系の方が自然
- ファイル送信やチャットイベント全体にはやや不向き

### 評価

今回のチャット用途では採用しない。

---

## 9.6 ポーリング

### メリット

- 実装が簡単
- WebSocketを使わなくても疑似リアルタイムにできる
- 障害時のフォールバックとして使える

### デメリット

- 無駄な通信が増える
- リアルタイム性が弱い
- 本格的なチャット体験には向かない

### 評価

MVPのフォールバックとしてはあり。  
メイン方式としては採用しない。

---

## 9.7 リアルタイム通信結論

Supabase Realtimeを採用する。

理由:

- Supabase PostgreSQLと連携しやすい
- 自前WebSocketサーバーが不要
- MVP開発の実装量を抑えられる
- リアルタイム更新要件を満たせる
- 将来的に必要ならSocket.IOへ拡張・移行を検討できる

---

## 10. ファイルストレージ選定

## 10.1 候補

| 候補 | 概要 |
|---|---|
| Supabase Storage | Supabaseのファイルストレージ |
| Firebase Storage | Firebaseのファイルストレージ |
| AWS S3 | AWSのオブジェクトストレージ |
| Cloudinary | 画像管理・変換に強いサービス |
| ローカル保存 | サーバー内に保存 |

---

## 10.2 Supabase Storage

### メリット

- Supabase Auth、DBと連携しやすい
- Storageにも権限制御を設定できる
- 画像・ファイル送信のMVPに向いている
- Supabaseにまとめられるため構成がシンプル
- ファイルURLをDBのメッセージと紐づけやすい

### デメリット

- 高度な画像変換や最適化はCloudinaryほど強くない
- 本番公開では公開範囲や署名付きURL設計が必要
- 大容量利用時はコスト確認が必要

### 評価

今回のMVPでは最適。

---

## 10.3 Firebase Storage

### メリット

- Firebase Authenticationと連携しやすい
- モバイル・Webアプリで実績が多い
- セキュリティルールでアクセス制御できる

### デメリット

- Firebase中心構成になりやすい
- DBをSupabase PostgreSQLにする場合、サービスが分散する

### 評価

Firebase構成なら良い。  
今回はSupabase Storageを優先する。

---

## 10.4 AWS S3

### メリット

- 本番運用で実績が非常に多い
- スケーラビリティが高い
- 署名付きURLなど細かい制御が可能
- 将来的な商用運用に強い

### デメリット

- 初期設定がやや複雑
- IAMやバケットポリシーの理解が必要
- 学習用MVPでは重くなりやすい

### 評価

本格本番公開時には有力。  
初期MVPでは採用しない。

---

## 10.5 Cloudinary

### メリット

- 画像変換、リサイズ、最適化に強い
- 画像中心アプリなら便利
- CDN配信も扱いやすい

### デメリット

- 一般ファイル管理にはS3やSupabase Storageの方が自然
- 今回は画像だけでなくファイル送信もある
- DBや認証とは別サービスになる

### 評価

画像処理を強化する段階で検討する。  
初期MVPでは採用しない。

---

## 10.6 ローカル保存

### メリット

- 実装が単純
- 外部サービス不要

### デメリット

- 本番公開に向かない
- デプロイ環境によってファイルが消える可能性がある
- 複数サーバー構成に弱い
- バックアップが面倒

### 評価

採用しない。

---

## 10.7 ファイルストレージ結論

Supabase Storageを採用する。

理由:

- Supabase Auth、DB、Realtimeと統合できる
- MVPの画像・ファイル送信に十分
- 構成がシンプル
- 将来的に本番公開する場合も権限制御を設計しやすい

---

## 11. バックエンド選定

## 11.1 候補

| 候補 | 概要 |
|---|---|
| Next.js Route Handlers / Server Actions | Next.js内でサーバー処理を書く |
| Node.js + Express | Node.jsの軽量バックエンド |
| NestJS | Node.jsの本格バックエンドフレームワーク |
| Django | PythonのフルスタックWebフレームワーク |
| Laravel | PHPのWebフレームワーク |
| Supabase中心 | バックエンド処理をSupabase機能に寄せる |

---

## 11.2 Next.js Route Handlers / Server Actions

### メリット

- フロントと同じリポジトリで管理できる
- TypeScriptで統一できる
- 小規模MVPでは構成がシンプル
- Supabaseとの連携を書きやすい
- Vercelにデプロイしやすい

### デメリット

- 大規模な業務ロジックには専用バックエンドの方が整理しやすい
- WebSocketサーバーを自前で持つ構成には向きにくい
- サーバーレス実行の制約を理解する必要がある

### 評価

今回のMVPでは最適。

---

## 11.3 Node.js + Express

### メリット

- シンプル
- Socket.IOと組み合わせやすい
- WebSocketサーバーを自前で持てる
- REST APIを明確に分離できる

### デメリット

- バックエンドプロジェクトが別になる
- デプロイ先を別途考える必要がある
- Supabaseを使う場合、MVPとしてはやや構成が増える

### 評価

Socket.IOを採用する場合は有力。  
今回はSupabase Realtimeを使うため、初期MVPでは採用しない。

---

## 11.4 NestJS

### メリット

- 大規模開発に向く
- 構造化されたバックエンドを作れる
- DIやモジュール設計を学べる
- WebSocketも扱える

### デメリット

- 学習コストが高め
- MVPにはやや重い
- フロントとは別プロジェクトになる

### 評価

本格的なバックエンド学習には良い。  
今回のMVPでは採用しない。

---

## 11.5 Django / Laravel

### メリット

- 認証、DB、管理画面などが強い
- サーバーサイド開発を学びやすい
- 実務実績が多い

### デメリット

- Next.js + Supabase構成とは方向性が異なる
- リアルタイム通信には追加設計が必要
- フロントとバックエンドが分かれやすい

### 評価

別方針なら有力。  
今回のMVPでは採用しない。

---

## 11.6 バックエンド結論

初期MVPでは、専用バックエンドを作らず、Next.js + Supabaseを中心にする。

理由:

- 実装量を抑えられる
- TypeScriptで統一できる
- Supabaseの機能を活かせる
- 学習用として全体像を把握しやすい
- 将来的に必要になれば、Node.js / NestJSバックエンドを追加できる

## 12.1 候補

## 12.2 Vercel

### メリット

- Next.jsとの相性が非常に良い
- GitHub連携で自動デプロイしやすい
- 学習用でも始めやすい
- 将来的な本番公開にも使える
- プレビュー環境を作りやすい

- バックエンドが重くなる場合は別サービスが必要
- 無料枠や制限を確認する必要がある

### 評価

Next.js + Supabase構成なら最適。

## 12.3 Netlify

### メリット

- 静的サイトやJamstackに強い
- Git連携が簡単

### デメリット

- Next.jsの場合はVercelの方が自然
- 今回の構成では積極的に選ぶ理由が薄い

### 評価

採用しない。

---

## 12.4 Render

### メリット

- Webサーバー、バックエンド、DBなどをまとめて扱いやすい
- Node.js + ExpressやNestJSを動かしやすい
- WebSocketサーバー構成に向く

### デメリット

- Next.jsだけならVercelの方が簡単
- Supabaseを使う場合、DBやStorageは別サービスになる

### 評価

専用バックエンドを作る場合に検討する。

---

## 12.5 Railway

### メリット

- バックエンド、DB、環境変数管理がしやすい
- 小規模アプリのデプロイが簡単
- WebSocketサーバーを持つ構成にも使いやすい

### デメリット

- Next.js + SupabaseだけならVercelの方が自然
- 利用量に応じたコスト確認が必要

### 評価

Socket.IO + Express構成なら候補。  
今回の初期MVPでは採用しない。

---

## 12.6 AWS

### メリット

- 本番運用で非常に強い
- スケーラビリティが高い
- S3、RDS、CloudFront、ECSなど選択肢が豊富

### デメリット

- 学習コストが高い
- 初期構築が重い
- コスト管理が難しい
- MVPには過剰

### 評価

将来的な本格運用では検討。  
初期MVPでは採用しない。

---

## 12.7 ホスティング結論

Vercelを採用する。

理由:

- Next.jsとの相性が良い
- GitHub連携で自動デプロイしやすい
- 学習用でも本番公開でも扱いやすい
- Supabaseをバックエンド基盤にすることで、Vercel側にWebSocketサーバーを持たなくてよい

## 17. セキュリティ方針

MVPでも以下は必ず行う。

- 未ログインユーザーのアクセス制限
- チャットルーム参加者チェック
- 自分が参加していないルームのメッセージ取得禁止
- 自分が参加していないルームへの送信禁止
- ファイルサイズ制限
- ファイル形式制限
- Supabase Row Level Securityの検討
- 公開してよいファイルと非公開ファイルの扱いを分ける
- `.env.local` をGitに含めない

本番公開前には以下を追加する。

- レート制限
- 監視
- バックアップ
- 利用規約
- プライバシーポリシー
- 通報機能
- 不適切ファイル対策
- エラー監視
- コスト監視

## 20. 採用理由まとめ

| 観点 | 理由 |
|---|---|
| 学習しやすさ | フロント、認証、DB、リアルタイム、ストレージを一通り学べる |
| 完成しやすさ | Supabaseにより実装量を抑えられる |
| 将来性 | PostgreSQLとNext.jsは本番公開にも使いやすい |
| 構成のシンプルさ | サービス数を抑えられる |
| リアルタイム対応 | Supabase RealtimeでMVP要件を満たせる |
| ファイル送信 | Supabase Storageで画像・ファイルを扱える |
| デプロイ | VercelでNext.jsを簡単に公開できる |
| セキュリティ | Supabase AuthとRLSを活用できる |
