# 本番想定チャットアプリ 技術構成案

## 1. 前提

本資料は、学習コストを考慮せず、本番公開・高性能・拡張性を重視したチャットアプリの技術構成案をまとめたものである。

対象は以下のようなチャットアプリを想定する。

- 1対1チャット
- 将来的なグループチャット対応
- リアルタイム更新
- 画像・ファイル送信
- 高い同時接続数
- 低レイテンシ
- 障害耐性
- 監視・ログ・バックアップ
- 将来的な大規模化

---

## 2. 結論

本番想定でベストパフォーマンスを狙うなら、以下の構成を推奨する。

| 分類 | 推奨技術 |
|---|---|
| フロントエンド | Next.js / React / TypeScript |
| CDN | CloudFront |
| 認証 | Auth0 / Amazon Cognito / Clerk |
| API Gateway | AWS API Gateway または ALB |
| WebSocketサーバー | Go + WebSocket / Socket.IO互換設計 |
| 実行基盤 | Kubernetes / Amazon EKS または ECS Fargate |
| メッセージDB | DynamoDB または ScyllaDB / Cassandra |
| メタデータDB | Aurora PostgreSQL |
| キャッシュ / Presence | Redis Cluster / ElastiCache |
| イベント基盤 | Kafka / Amazon MSK または NATS JetStream |
| ファイル保存 | Amazon S3 |
| ファイル配信 | CloudFront Signed URL / Signed Cookie |
| 検索 | OpenSearch |
| 非同期処理 | SQS / Kafka consumers / worker service |
| 監視 | CloudWatch / Prometheus / Grafana / OpenTelemetry |
| エラー監視 | Sentry |

## 5. なぜSupabase一体型ではなく分離構成にするのか

SupabaseはMVPや中小規模には非常に便利だが、本番で高性能を狙う場合は以下の課題が出やすい。

- WebSocket接続数を細かく制御しにくい
- 独自のリアルタイムイベント設計に制約がある
- 大規模なPresence管理に向けた設計が必要
- 大量メッセージ保存でDB設計をより最適化したくなる
- ファイルスキャン、検索、通知などの非同期処理が増える
- 障害分離が難しくなる

本番高性能構成では、以下を分離する。

- 画面表示
- 認証
- WebSocket接続管理
- メッセージ保存
- イベント配信
- ファイル保存
- 通知
- 検索
- 監視

これにより、負荷が増えた部分だけ個別にスケールできる。

## 7. 認証

### 推奨候補

- Auth0
- Amazon Cognito
- Clerk

### Auth0

#### メリット

- エンタープライズ向け機能が強い
- SSO、MFA、組織管理などに強い
- セキュリティ要件が高い本番に向く

#### デメリット

- 小規模には高機能すぎる
- コストが上がりやすい
- 設定が複雑になりやすい

### Amazon Cognito

#### メリット

- AWS構成と統合しやすい
- IAM、API Gateway、ALBなどと連携しやすい
- 大規模利用に向く

#### デメリット

- 開発体験はAuth0やClerkより難しく感じやすい
- UIやユーザー管理の作り込みに工夫が必要

### Clerk

#### メリット

- Next.jsとの相性が良い
- 認証UIを作りやすい
- 開発体験が良い

#### デメリット

- AWS完全統合という観点ではCognitoに劣る
- 大規模エンタープライズ要件ではAuth0やCognitoと比較が必要

### 結論

AWS中心で本番高性能構成を作るなら Amazon Cognito。  
認証体験と開発効率を重視するなら Auth0 または Clerk。

厳密な「AWS統合・大規模運用」重視なら Cognito を推奨する。

## 8. リアルタイム通信

### 推奨

Go製WebSocket Gateway + Kubernetes / ECS

### 理由

チャットアプリでは、リアルタイム通信部分が性能の中心になる。

必要な処理:

- WebSocket接続管理
- 認証済み接続の検証
- チャットルーム参加管理
- ユーザーごとの接続状態管理
- メッセージ送信イベント
- メッセージ受信イベント
- 再接続
- 多重接続対応
- ハートビート
- レート制限
- Presence管理

これらを細かく制御するには、マネージドRealtimeより自前WebSocket Gatewayの方が自由度が高い。

### Goを選ぶ理由

- 並行処理に強い
- 軽量
- WebSocket接続を大量に扱いやすい
- メモリ効率が良い
- 単一バイナリでデプロイしやすい
- 高負荷なリアルタイムサーバーに向く

### 代替候補

| 候補 | 特徴 |
|---|---|
| Node.js + Socket.IO | 開発しやすいが、超高負荷ではGoより工夫が必要 |
| Elixir / Phoenix Channels | リアルタイム通信に非常に強い |
| Java / Kotlin | 堅牢だが実装量が増えやすい |
| API Gateway WebSocket | 運用は楽だが細かい制御や超低遅延では自前サーバーに劣る場合がある |

## 9. メッセージ保存DB

### 推奨候補

- DynamoDB
- ScyllaDB
- Cassandra
- Aurora PostgreSQL

### DynamoDB

#### メリット

- フルマネージド
- 低レイテンシ
- 大規模スケールに強い
- パーティションキー設計がハマればチャット履歴保存に向く
- 運用負荷が低い

#### デメリット

- クエリ設計を先に決める必要がある
- RDBのような柔軟なJOINはできない
- アクセスパターンを間違えると使いにくい
- ベンダーロックインが強い

### ScyllaDB / Cassandra

#### メリット

- 大量書き込みに強い
- 低レイテンシ
- 水平スケールしやすい
- メッセージ履歴のような時系列データに向く

#### デメリット

- 運用が難しい
- データモデリングに慣れが必要
- 強い整合性が必要な処理には注意

### Aurora PostgreSQL

#### メリット

- RDBとして扱いやすい
- トランザクションに強い
- JOINや集計がしやすい
- 管理画面や運用系データに向く

#### デメリット

- 超大量メッセージ保存の主DBとしてはNoSQL系よりスケール設計が難しい
- 書き込み負荷が集中しやすい
- シャーディングが必要になる可能性がある

### 結論

本番高性能チャットでは、メッセージ本文の保存は DynamoDB または ScyllaDB を推奨する。

AWS中心で運用負荷を下げるなら DynamoDB。  
超低レイテンシ・高スループットを自前で突き詰めるなら ScyllaDB。

メタデータや管理系データは Aurora PostgreSQL に分ける。

## 11. Redisの役割

### 推奨

ElastiCache Redis Cluster

### 用途

- Presence管理
- オンライン状態
- ユーザーIDとWebSocket接続IDの対応
- 短期キャッシュ
- レート制限
- 一時的なPub/Sub
- 未読数の一時キャッシュ

### 注意点

Redis Pub/Subは軽く速いが、永続性や再送保証は主目的ではない。  
重要なメッセージ配送保証にはKafkaやNATS JetStreamなどを併用する。

## 12. イベント基盤

### 推奨候補

- Kafka / Amazon MSK
- NATS JetStream
- Redis Streams

### Kafka

#### メリット

- 高スループット
- イベントログとして強い
- 複数のコンシューマーで後続処理を分離できる
- 通知、検索インデックス、分析、監査ログに向く

#### デメリット

- 運用が重い
- 学習コストが高い
- 小規模には過剰

### NATS JetStream

#### メリット

- 軽量
- 低レイテンシ
- Pub/Subと永続化を扱える
- リアルタイム寄りのイベント処理に向く

#### デメリット

- Kafkaほど巨大なイベントログ基盤としての標準感はない
- チームの経験値が必要

### 結論

大規模なイベント連携・分析・監査を重視するなら Kafka / MSK。  
低レイテンシで軽量なリアルタイムイベント基盤を重視するなら NATS JetStream。

チャットアプリでは、以下のように使い分ける。

- 即時配信: WebSocket Gateway + Redis
- 永続イベント: Kafka または NATS JetStream
- メッセージ保存: DynamoDB / ScyllaDB

## 13. ファイル保存・配信

### 推奨

- Amazon S3
- CloudFront
- Presigned URL
- Signed URL / Signed Cookie

### アップロード方式

```text
1. クライアントがAPIへアップロード要求
2. APIが認証・権限・ファイルサイズ・形式を確認
3. APIがS3 Presigned URLを発行
4. クライアントがS3へ直接アップロード
5. APIへアップロード完了を通知
6. メッセージDBに添付情報を保存
7. CloudFront経由で配信
```

### 理由

アプリサーバーを経由してファイル本体をアップロードすると、サーバー負荷が大きくなる。  
Presigned URLでS3へ直接アップロードさせることで、アプリサーバーの負荷を減らせる。

### 本番で必要なこと

- ファイルサイズ制限
- MIME type検証
- 拡張子制限
- ウイルススキャン
- 非公開バケット
- 署名付きURL
- CDN配信
- 保存期間ポリシー
- 不適切ファイル通報
- コスト監視

## 23. まとめ

学習用なら Supabase + Next.js がよい。  
本番で高性能を狙うなら、分離構成にする。

特に重要なのは以下。

- WebSocket接続管理を専用サーバーにする
- メッセージ保存は高書き込み性能のDBにする
- メタデータはRDBに分ける
- PresenceはRedisに分ける
- 通知や検索はイベント基盤で非同期化する
- ファイルはS3に直接アップロードする
- 配信はCloudFrontを使う
- 監視、ログ、レート制限、WAFを最初から入れる

本番チャットアプリは、単なるCRUDアプリではなく、リアルタイム分散システムとして設計する必要がある。
