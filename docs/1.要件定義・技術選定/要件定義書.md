# チャットWebアプリ 要件定義書

## 1. 概要

本資料は、チャットWebアプリの要件定義をまとめたものである。  
本アプリは、ユーザー同士が1対1でリアルタイムにメッセージを送受信できるWebアプリとして開発する。

本プロジェクトでは、まずMVPとして必要最低限の機能を実装し、その後に機能追加や改善を行う。

---

## 2. 開発目的

### 目的

- 1対1チャットができるWebアプリを開発する
- 外部認証を利用して安全にログインできるようにする
- メッセージをリアルタイムに送受信できるようにする
- 画像・ファイル送信に対応する
- 開発工程ごとに資料をMarkdownで残す
- 要件定義からリリースまでの開発プロセスを実践する

---

## 3. 想定ユーザー

### 一般ユーザー

アプリにログインして、他のユーザーと1対1でチャットするユーザー。

### 管理者

初期開発では管理者機能は実装しない。  
将来的な拡張として、ユーザー管理、通報確認、メッセージ監視、利用停止などを検討する。

---

## 4. MVP要件

本プロジェクトのMVPでは、以下を対象とする。

| 項目 | 方針 |
|---|---|
| チャット形式 | 1対1チャット |
| 認証 | 外部認証を利用する |
| リアルタイム更新 | MVPに含める |
| 画像送信 | MVPに含める |
| ファイル送信 | MVPに含める |
| 管理者機能 | 初期開発には含めない |
| スマホ対応 | 後回し |
| 本番公開 | 方針検討対象 |
| 学習用 | 方針検討対象 |

---

## 5. 機能要件

## 5.1 認証機能

### 概要

外部認証サービスを利用してログインできるようにする。

### 要件

- ユーザーは外部認証を使ってログインできる
- ログイン後、自分のユーザー情報を取得できる
- ログアウトできる
- 未ログインユーザーはチャット画面にアクセスできない
- 認証済みユーザーのみメッセージを送信できる

### 補足

外部認証の候補は技術選定工程で決める。

候補:

- Firebase Authentication
- Auth0
- Supabase Auth
- Clerk
- AWS Cognito

---

## 5.2 ユーザー機能

### 概要

チャット相手を識別するために、アプリ内でユーザー情報を管理する。

### 要件

- 外部認証IDとアプリ内ユーザーを紐づける
- ユーザー名を表示できる
- ユーザー一覧を取得できる
- 自分以外のユーザーをチャット相手として選択できる

### MVPで扱うユーザー情報

- ユーザーID
- 外部認証ID
- 表示名
- アイコンURL
- 作成日時
- 更新日時

---

## 5.3 1対1チャット機能

### 概要

ユーザー同士が1対1でチャットできる。

### 要件

- ユーザーはチャット相手を選択できる
- 選択した相手とのチャットルームを作成できる
- 既にチャットルームがある場合は既存ルームを利用する
- 自分が参加しているチャットルーム一覧を表示できる
- 自分が参加していないチャットルームにはアクセスできない

---

## 5.4 メッセージ送信機能

### 概要

チャットルーム内でテキストメッセージを送信できる。

### 要件

- テキストメッセージを送信できる
- 空文字のメッセージは送信できない
- 送信したメッセージはDBに保存される
- メッセージには送信者、送信日時、チャットルームIDを紐づける
- メッセージ送信後、相手の画面にリアルタイムで反映される

---

## 5.5 メッセージ表示機能

### 概要

チャットルーム内のメッセージ履歴を表示する。

### 要件

- チャットルームのメッセージ一覧を取得できる
- 古いメッセージから新しいメッセージの順に表示する
- 送信者が自分か相手か分かるように表示する
- 送信日時を表示する
- 新しいメッセージをリアルタイムに追加表示する

---

## 5.6 リアルタイム更新機能

### 概要

メッセージ送信後、相手の画面に自動反映されるようにする。

### 要件

- チャットルーム単位でリアルタイム接続する
- メッセージ送信時に相手へイベントを配信する
- 受信側は画面を再読み込みせずにメッセージを表示できる
- 接続が切れた場合の最低限の再接続を考慮する
- ページ再読み込み時にはDBから最新メッセージを取得する

### 技術候補

- WebSocket
- Socket.IO
- Supabase Realtime
- Firebase Realtime Database / Firestore
- Server-Sent Events

最終決定は技術選定工程で行う。

---

## 5.7 画像送信機能

### 概要

チャット内で画像を送信できる。

### 要件

- ユーザーは画像ファイルを選択して送信できる
- 送信された画像はストレージに保存される
- メッセージには画像URLを紐づける
- チャット画面上で画像を表示できる
- 対応する画像形式を制限する
- ファイルサイズ上限を設ける

### MVPで想定する制限

- 対応形式: jpg, jpeg, png, webp
- 最大サイズ: 技術選定後に決定
- 複数枚同時送信: 初期開発では後回し

---

## 5.8 ファイル送信機能

### 概要

チャット内でファイルを送信できる。

### 要件

- ユーザーはファイルを選択して送信できる
- ファイルはストレージに保存される
- メッセージにはファイルURL、ファイル名、ファイルサイズを紐づける
- チャット画面からファイルをダウンロードできる
- ファイル形式とサイズに制限を設ける

### MVPで想定する制限

- 危険な拡張子は許可しない
- 最大サイズ: 技術選定後に決定
- ウイルススキャン: 学習用では省略、本番公開では検討

---

## 7. 非機能要件

## 7.1 セキュリティ

### 共通

- 未ログイン状態ではチャット機能を利用できない
- 自分が参加していないチャットルームにはアクセスできない
- 外部認証IDを信用しすぎず、アプリ側のユーザー情報と紐づけて管理する
- ファイルアップロードにはサイズ制限を設ける
- 許可するファイル形式を制限する
- API側でも権限チェックを行う

### 本番公開の場合に特に必要

- HTTPS必須
- CORS設定
- レート制限
- アップロードファイルの検証
- 個人情報の取り扱い整理
- 利用規約・プライバシーポリシー
- ログに個人情報を出しすぎない
- エラー内容をユーザーに詳細表示しすぎない
- 不正アクセス対策
- バックアップ
- 監視

---

## 7.2 性能

### MVP

- 少人数での利用を想定する
- メッセージ一覧は必要に応じてページングまたは件数制限する
- 画像・ファイルはDBに直接保存せず、ストレージに保存する

### 将来的な検討

- 大量メッセージ対策
- 無限スクロール
- メッセージ検索
- キャッシュ
- CDN
- WebSocket接続数の管理

---

## 7.3 可用性

### 学習用

- 常時稼働は必須ではない
- 手動デプロイでもよい
- 障害時は手動復旧でもよい

### 本番公開

- 障害時の復旧手順が必要
- DBバックアップが必要
- ストレージの保全が必要
- 監視とアラートが必要
- リリース前の切り戻し手順が必要

---

## 7.4 保守性

- Markdown資料を残す
- API仕様を明文化する
- DB変更はマイグレーションで管理する
- 環境変数のサンプルを残す
- READMEに起動手順を書く
- 仕様変更は `change-log.md` に記録する

| 画面 | 内容 |

- 自分が参加していないチャットルームにはメッセージを送信できない

### 管理者

初期開発では対象外。

## 12. 本番公開と学習用の違い

## 12.1 大きく変わる点

本番公開と学習用では、主に以下が変わる。

| 項目 | 学習用 | 本番公開 |
|---|---|---|
| 目的 | 技術理解・ポートフォリオ | 実ユーザーに提供 |
| 認証 | 動けばよい構成でも可 | 安全性・設定確認が重要 |
| セキュリティ | 最低限 | 必須レベルが高い |
| ファイル送信 | サイズ制限程度でも可 | 不正ファイル対策が必要 |
| 個人情報 | ダミーデータ中心 | 取り扱いルールが必要 |
| 監視 | 省略可 | エラー監視・ログ確認が必要 |
| バックアップ | 省略または手動 | 定期バックアップが必要 |
| 利用規約 | 省略可 | 必要 |
| プライバシーポリシー | 省略可 | 必要 |
| コスト管理 | 無料枠中心 | 利用増加時の費用設計が必要 |
| 障害対応 | 手動確認で可 | 復旧手順が必要 |
| リリース手順 | 簡易で可 | 手順書・切り戻しが必要 |

---

## 12.2 学習用の場合

### 方針

学習用では、開発プロセスと実装理解を優先する。

### 優先すること

- 要件定義からリリースまで一通り経験する
- 認証、DB、API、リアルタイム通信、ファイルアップロードを実装する
- Markdown資料を残す
- ローカル環境と簡易デプロイを経験する
- ポートフォリオとして説明できる状態にする

### 省略または簡略化できること

- 高度なセキュリティ対策
- 本格的な監視
- 自動バックアップ
- 利用規約
- プライバシーポリシー
- SLA
- 大量アクセス対策
- ウイルススキャン
- 管理者画面

---

## 12.3 本番公開の場合

### 方針

本番公開では、実ユーザーのデータを扱う前提で、安全性と運用性を重視する。

### 必要になること

- HTTPS
- 認証設定の安全確認
- API権限チェック
- レート制限
- ファイルアップロード制限
- ファイル保存先の公開範囲制御
- 個人情報の扱い整理
- 利用規約
- プライバシーポリシー
- DBバックアップ
- ストレージバックアップ
- エラー監視
- アクセスログ
- リリース手順書
- 切り戻し手順
- 障害対応手順
- コスト監視

### 特に注意すること

チャットアプリは、ユーザーが自由にテキストやファイルを送れるため、本番公開では以下のリスクがある。

- 不適切な投稿
- 個人情報の投稿
- 危険なファイルのアップロード
- スパム
- 大量メッセージ送信
- なりすまし
- 不正アクセス
- ストレージ容量の急増
- WebSocket接続数の増加

そのため、本番公開を目指す場合は、MVPでも最低限の制限や監視が必要になる。

## 13. 本プロジェクトの推奨方針

現時点では、以下の方針を推奨する。

### 推奨

まずは「学習用 + 将来的に本番公開できる構成」で作る。

### 理由

最初から本番レベルにしすぎると、実装前の準備が重くなる。  
一方で、学習用として雑に作りすぎると、後から本番公開へ移行しにくい。

そのため、以下のように分ける。

### MVPで必ずやる

- 外部認証
- 1対1チャット
- リアルタイム更新
- 画像・ファイル送信
- API側の認証チェック
- チャットルーム参加者チェック
- ファイルサイズ制限
- ファイル形式制限
- Markdown資料管理
- 簡易デプロイ

### MVPでは簡略化する

- 管理者機能
- スマホ最適化
- 通報機能
- ブロック機能
- ウイルススキャン
- 利用規約
- プライバシーポリシー
- 高度な監視
- 自動バックアップ

### 本番公開前に追加する

- 利用規約
- プライバシーポリシー
- レート制限
- エラー監視
- バックアップ
- ログ管理
- 通報機能
- ファイル安全対策
- コスト監視
- リリース手順書
- 切り戻し手順

## 14. 受入条件

MVP完了の条件は以下。

- 外部認証でログインできる
- ログインしていないユーザーはチャット画面に入れない
- ユーザー一覧から相手を選べる
- 1対1チャットルームを作成できる
- 既存の1対1チャットルームを再利用できる
- メッセージを送信できる
- メッセージ履歴を表示できる
- 相手の画面にリアルタイムでメッセージが表示される
- 画像を送信できる
- ファイルを送信できる
- 自分が参加していないチャットルームにはアクセスできない
- PC画面で基本操作ができる
- スマホ最適化は未対応でもよい
- 管理者機能は未実装でよい
